**Date:** 2026-07-25 · **Scope:** whole module (~32k LOC) — `encoder`, `embed`, `linalg`, `ann`, `bm25`, `sparse`, `topk`, `fuse`, `chunk` (+ `treesitter`/`markdown`/`regex`), `vision`, `mmap`, `bench`, `benchmarks`
**Categories:** bugs & correctness, performance, architecture & maintainability

**Method.** Source read in full for the highest-LOC packages, with callers traced before anything was called a bug. Every finding quotes the code it rests on. Findings #1, #6, #8 and #15 were independently re-verified against the tree after the fact.

**Verification note.** `go vet` / `golangci-lint` could not be run in the audit environment (`go.mod` requires a newer toolchain than was available and the module proxy was unreachable), so this is a reading-based audit. Nothing below depends on tooling output.

## Critical & High

### 1. `LoadWeights` (the only mmap loader) never reads `1_Pooling/config.json` — mean-pooling checkpoints are silently CLS-pooled

**Severity: High** — `encoder/weights.go:207`

`LoadWeightsFromFS` populates the pooling mode; `LoadWeights` does not:

```go
// weights.go:241 (LoadWeightsFromFS)
if cfg.pooling, err = poolingFromFS(fsys, dir, poolCLS); err != nil {
```
```go
// weights.go:207 (LoadWeights) — no equivalent line
func LoadWeights(dir string) (*Weights, error) {
	cfg, err := loadConfig(os.DirFS(dir), "config.json")
	...
	if err := cfg.ValidateAssumptions(); err != nil { ... }
	st, err := embed.OpenSafetensorsMmap(filepath.Join(dir, "model.safetensors"))
	...
	return buildWeightsFromSafetensors(cfg, st)
}
```

`buildWeightsFromSafetensors` copies `Cfg: *cfg`, so `Cfg.pooling` stays `""`, and `poolOne` treats `""` as `poolCLS` (`pooling.go:103`). `weights.go:241` is the only non-test assignment to `cfg.pooling`.

**Failure scenario.** `encoder.LoadWeights("<nomic-embed-text-v1.5>")` — whose `1_Pooling/config.json` sets `pooling_mode_mean_tokens: true`, as `weights.go:239-240`'s own comment states — returns CLS-pooled vectors. Every embedding is wrong (not merely noisy: a different reduction), retrieval quality collapses, and nothing errors. `LoadQ8` inherits it via `weights_q8.go:67 → LoadWeights(dir)`, so the comment at `forward_q8.go:63-65` ("the Q8 path used to hardcode CLS, so a mean-pooling checkpoint would silently return CLS") describes a fix that is inert on the disk path. `nomic_embed_test.go:27` and `nomic_moe_test.go:35` only exercise the FS loader.

**Fix.** In `LoadWeights`, after `ValidateAssumptions`, add the disk-path equivalent (the helper already exists and is used by `bert.go:193`):

```go
if cfg.pooling, err = poolingFromConfig(dir, poolCLS); err != nil { return nil, err }
```

### 2. `encoder.Load` — the documented public entry point — bypasses the mmap loader and heap-reads the whole checkpoint

**Severity: High** — `encoder/model.go:40`

```go
func Load(dir string) (*Model, error) {
	return LoadFromFS(os.DirFS(dir), ".")
}
```

`LoadFromFS` → `LoadWeightsFromFS` → `embed.OpenSafetensorsFromFS` → `fs.ReadFile` (`safetensors.go:134`): a full heap copy. `LoadWeights`, the mmap path added expressly so "the 547 MB CodeRankEmbed checkpoint stays in the OS page cache instead of dominating Go heap RSS" (`weights.go:201-203`), has **no caller** except `LoadWeightsQ8` — `LoadWeights(` appears only at `weights_q8.go:67` and `weights_test.go:23`.

**Failure scenario.** `examples/rag/main.go:68` and `example_test.go:17` both call `encoder.Load`. On CodeRankEmbed that is ~547 MB of Go heap per process, GC-scanned, with no page-cache sharing between processes — the exact regression M8 was written to fix. Compounding it, `Model.Close()` (`model.go:78`) documents itself as releasing "the mmap-backed weights", but for any `Model` built via `Load`/`LoadFromFS` `st.mmapped` is empty and `Close` only flips the `closed` flag.

**Fix.** Give `Model` a disk constructor that uses the mmap loader — `Load(dir)` should call `LoadWeights(dir)` plus `embed.LoadTokenizer(filepath.Join(dir, "tokenizer.json"))`, keeping `LoadFromFS` as the `fs.FS`/`embed.FS` route. Fix #1 first, or `Load` regresses pooling.

### 3. Attention biases are silently dropped by the Q8 forward (always) and by the batched f32 forward

**Severity: High** — `encoder/weights_q8.go:88`, `encoder/attention_batch.go:23`

The single-sequence f32 path threads both biases:

```go
// forward.go:83
selfAttention(h, l.Wqkv, l.WqkvB, l.OutProj, l.OutProjB, heads, headDim, D, L, rope, s)
```

The batched f32 path has no bias parameters at all:

```go
// attention_batch.go:23
func selfAttentionBatched(h []float32, Wqkv, OutProj []float32, heads, headDim, D, B, Lmax int, ...)
// forward_batch.go:125
selfAttentionBatched(h, l.Wqkv, l.OutProj, heads, headDim, D, B, Lmax, realLen, rope, s)
```

And `LayerWeightsQ8` (`weights_q8.go:21-34`) declares no bias fields, so `LoadWeightsQ8` never copies `WqkvB`/`OutProjB` and `selfAttentionQ8`/`selfAttentionQ8Batched` (`forward_q8.go:139`, `:194`) cannot apply them.

The only guard is `forward_batch.go:54` / `weights_q8.go:74`: `if w.hasMoE() || !w.Cfg.gatedMLP()`. `ValidateAssumptions` (`weights.go:86-137`) does **not** reject `QKVProjBias` alongside a gated MLP, and `weights.go:291` loads the biases whenever `cfg.QKVProjBias` is true.

**Failure scenario.** A SwiGLU, non-MoE checkpoint with `qkv_proj_bias: true` (the loader explicitly supports this shape) loads without error. `Encode` applies the biases and is correct; `EncodeBatch` on the same model omits them, so query and document vectors computed through different entry points live in different spaces and cosine ranking is garbage. `LoadQ8` on that checkpoint drops them on *every* path. `TestForwardBatch_matchesSingle` cannot catch it — the fixtures are bias-free.

**Fix.** Thread `WqkvB`/`OutProjB` through `selfAttentionBatched` and `addRowBias` them exactly as `attention.go:35,94` does; add the two bias fields to `LayerWeightsQ8` (copy them f32 — they are `[3D]`/`[D]`). Until that lands, make it loud: reject `cfg.QKVProjBias` in `ValidateAssumptions` for the batched/Q8 paths rather than mis-scoring.

### 4. `vision` integer divide-by-zero panic on a zero-patch grid

**Severity: High** — `vision/qwen_encoder.go:292`

```go
	nPatches += g[0] * g[1] * g[2]        // :270
...
	if len(pixelValues) != nPatches*patchDim { ... }   // :272 — 0 != 0 is false
	if nPatches%mergeUnit != 0 { ... }                 // :275 — 0 % 4 == 0
...
	rdim := len(freqs) / nPatches         // :292
```

Validation at `:264-269` rejects negative dims and non-`merge`-divisible `h`/`w`, but not zero. `nPatches == 0` passes both subsequent guards, `rotaryFreqs` returns nil, and line 292 divides by zero.

**Failure scenario.** `enc.Forward(nil, nil)` — or `[][3]int{{1,0,0}}`, `{{0,2,2}}` — panics with `runtime error: integer divide by zero` instead of returning an error. A server that builds `gridTHW` from a request's image list and reaches the encoder with zero images (or a smart-resize that rounds a tiny image to a zero grid) crashes the process. `ForwardViT` (`:353`) shares the path.

**Fix.** Reject `g[0] <= 0 || g[1] <= 0 || g[2] <= 0` in the loop at `:264`, and return early when `len(gridTHW) == 0`. Better still, derive `rdim` from `len(e.rotInvFreq)*2` and delete the division.

### 5. Both vision towers reallocate every scratch buffer — including the O(np²) score matrix — on every layer

**Severity: High (performance)** — `vision/encoder.go:278`

```go
	out := make([]float32, np*hidden)
	qh := make([]float32, np*hd)
	kh := make([]float32, np*hd)
	vt := make([]float32, hd*np)
	scores := make([]float32, np*np)
	oh := make([]float32, np*hd)
```

`attention` is called once per layer from `for l := range e.layers` (`:224`), and `layerNorm` (`:311`) plus `o`/`mid`/`mlp` (`:229,238,242`) each `make` a fresh output per call. Every shape is identical on every layer. `vision/qwen_encoder.go:388-422,325-337` is the same pattern.

**Failure scenario.** SigLIP-so400m (`image_size=896, patch_size=14` ⇒ `np=4096`, `hidden=1152`, `inter=4304`, 27 layers). `scores` alone is 4096·4096·4 = 67 MB per layer; `mid` is 70 MB; q/k/v/out/oh/n1/n2/mlp add ~150 MB. That is ≈290 MB allocated and discarded **per layer**, ≈7.9 GB per image, all of it trivially reusable. The GC and page-fault churn on repeated 67 MB spans is a large fraction of wall time on a CPU forward.

**Fix.** Allocate the set once per `Forward` (a `visionScratch` struct, or `ensureF32`-style grow-on-demand buffers like `encoder/scratch.go`) and pass them as `dst` parameters. One scratch per `Forward` call preserves the documented concurrent-`Forward` safety. While there, the `vt` transpose at `:286-288` writes with stride `np` (16 KB at np=4096) — one cache miss per element, ~127 M per image; transpose `v` once for all heads.

### 6. `topk.Selector` evicts the wrong tied incumbent, breaking the tie-break contract `bm25.TopK` and `sparse.Query` document

**Severity: High** — `topk/topk.go:92`

```go
	if score <= s.heap[0].score {
		return false
	}
	s.heap[0] = scored[T]{item: item, score: score}
	s.siftDown(0)
```

Strict `>` correctly rejects a tied *newcomer*, but `heap[0]` is *a* minimum, not the *first-seen* one — so a higher score arriving later can evict an older tied item and leave a newer one.

**Failure scenario (k=2), traced through the actual heap ops:** `Push(d0,5)` → `heap=[{d0,5}]`. `Push(d1,5)` → `siftUp(1)` returns immediately (`5 >= 5`, line 143) → `heap=[{d0,5},{d1,5}]`, root `d0`. `Push(d2,10)` → `10 > 5` → `heap[0]={d2,10}`, `siftDown(0)` swaps → `heap=[{d1,5},{d2,10}]`. **`d0` dropped, `d1` kept.**

In `bm25.Build([][]string{{"cat"},{"cat"},{"cat","cat"}})` with query `["cat"], k=2`: doc0 and doc1 tie, doc2 is higher. The `k>=0` heap path returns `[{Doc:2},{Doc:1}]`; the `k<0` full-sort path (`bm25/query.go:95`) returns doc2, doc0, doc1, whose top-2 is `[{Doc:2},{Doc:0}]`. The two documented paths of the same function disagree, and `query.go:68` promises "ties broken by ascending document id so results are deterministic". The trailing `sort.SliceStable` (`query.go:116`, `sparse/sparse.go:149`) can only reorder what survived — it cannot recover doc0. `topk/topk_test.go:86` misses it because it pushes the tied item first (already at the root); `sparse/sparse_test.go:101` uses k=10 with 2 scoring docs so the heap never fills.

**Fix.** Add a monotonic insertion counter to `Selector` and order the heap on `(score asc, seq desc)` so the root is the *latest*-inserted tied minimum. `Push`'s strict `>` and the callers' stable sort then both match the contract.

### 7. `markdown.subdivideSection` is O(L²) in lines whenever a section has no blank lines

**Severity: High (performance)** — `chunk/markdown/markdown.go:180`

```go
	for i := 1; i < len(lines); i++ {
		accumBytes := lines[i].end - lines[chunkStartIdx].start
		if accumBytes >= chunkSize && i > chunkStartIdx {
			splitIdx := -1
			for s := i; s > chunkStartIdx; s-- {
				if splittable[s] { splitIdx = s; break }
			}
			if splitIdx > chunkStartIdx { ... chunkStartIdx = splitIdx + 1 }
			// no split found ⇒ chunkStartIdx unchanged
		}
	}
```

When the backward scan finds nothing, `chunkStartIdx` doesn't advance, so the next `i` rescans the whole `(chunkStartIdx, i]` range again. `splittablePositions` (`:218`) marks **only** `lineBlank`, and blank lines inside a fence are classified `lineCodeInside` (`scanner.go:114`) — so any long stretch without a real blank line makes `splittable` all-false and the inner loop degenerates to Σi ≈ L²/2.

**Failure scenario.** A `.md` file embedding a large generated artifact in one fenced block (JSON dump, SQL schema, terminal transcript) — routine in a docs corpus. 20,000 lines → 200 M inner iterations; 100,000 lines → ~5 G, on top of emitting one oversized chunk. The comment at `:140` records fixing an earlier O(N²/chunkSize) rescan as "M5"; this second quadratic in the same function survived.

**Fix.** One O(L) prefix pass — `prevSplit[i] = max{s ≤ i : splittable[s]}` (else −1) — then `splitIdx := prevSplit[i]`. Exactly equivalent (the old loop also returned the greatest splittable ≤ i, and the `> chunkStartIdx` guard is unchanged).

### 8. Frontmatter delimiter is stored untrimmed but compared trimmed — one trailing space collapses the whole document into a single chunk

**Severity: High** — `chunk/markdown/scanner.go:121`

```go
	if i == 0 && isFrontmatterOpen(body) {
		inFrontmatter = true
		frontmatterDelim = append([]byte(nil), body...)   // UNtrimmed
```
```go
func isFrontmatterOpen(body []byte) bool {
	trimmed := bytes.TrimRight(body, " \t")               // :228 — trims
	return bytes.Equal(trimmed, []byte("---")) || bytes.Equal(trimmed, []byte("+++"))
}
func isFrontmatterClose(body, delim []byte) bool {
	trimmed := bytes.TrimRight(body, " \t")               // :236 — trims
	return bytes.Equal(trimmed, delim)
}
```

Open decides on the trimmed line but records the raw one; close compares trimmed-vs-raw.

**Failure scenario.** A file whose first line is `---` plus one trailing space (invisible; editors and copy-paste produce it constantly). `delim = "--- "`; the closing `---` trims to `"---"`, `Equal` fails, `inFrontmatter` never clears. Every remaining line becomes `lineFrontmatterInside` (`:102`), so no `lineHeadingATX` ⇒ `boundaries == [0]` (`markdown.go:120`) and no `lineBlank` ⇒ `splittable` all-false. The entire document, at any size, returns as **one chunk** — all heading sections lost, `chunkSize` and any downstream token limit blown — and it simultaneously triggers finding #7's quadratic.

**Fix.** `frontmatterDelim = append([]byte(nil), bytes.TrimRight(body, " \t")...)`.

## Medium

### 9. `FlatI8.PageStats` reads the `SpanCache` counters without `pagerMu` — data race

**Severity: Medium** — `ann/flat_i8_mmap.go:132`

`scorePaged` serializes correctly (`:114-115` `f.pagerMu.Lock(); defer f.pagerMu.Unlock()`), but `PageStats` does not:

```go
	h, m, e := f.pager.Stats()
	return h, m, e, true
```

`SpanCache` is documented "Not goroutine-safe" (`mmap/spancache.go:22`) and `Touch` mutates exactly what `Stats()` reads (`spancache.go:84 c.hits++`, `:87 c.misses++`, `:99 c.evictions++`; `Stats` at `:128`). `FlatI8.Query` is documented concurrent-safe (`flat_i8_mmap.go:71-74`).

**Failure scenario.** A server running `Query` on request goroutines while a metrics goroutine scrapes `PageStats()` is an unsynchronized read/write on three `int64`s — a hard `-race` failure and, under the Go memory model, an unordered read. `TestFlatI8_pagedConcurrentQueries` fans out `Query` across 8 goroutines but calls `PageStats` single-threaded, so it is latent.

**Fix.** Take `f.pagerMu` around the `Stats()` call — uncontended and O(1).

### 10. MoE FFN applies `W2` with a scalar triple loop while every other projection is SIMD

**Severity: Medium (performance)** — `encoder/mlp.go:134`

```go
			for i := range intermediate {
				wRow := expW2[i*D : (i+1)*D]
				xi := x1[i]
				if xi == 0 { continue }
				for j := range D {
					out[j] += best * xi * wRow[j]
				}
			}
```

Plus three per-call allocations that bypass the existing scratch arena:

```go
	scores := make([]float32, numExperts)   // :101
	x1 := make([]float32, intermediate)     // :102
	out := make([]float32, D)               // :103
```

`W2` is `[intermediate, D]` and applied untransposed, so it can't use `matmulBTInto` as stored — hence the scalar fallback. Every other projection in the package routes through the SIMD kernel; the comment at `attention.go:53-55` notes the analogous scalar `scores·V` loop was "the single hottest line in Encode (≈⅓ of total)" before it was vectorized.

**Failure scenario.** nomic-embed-text-v2-moe, `D=768`, `intermediate=384`, `topK=2`: 2·384·768 ≈ 590k scalar FMAs per token per MoE layer, times L tokens times 6 MoE layers — the dominant cost of the v2-moe forward, at roughly the 3-5× penalty the NEON/AVX2 kernel would remove. `moeMLP` is also invoked once per layer, so `make` runs `NumLayers/2` times per forward.

**Fix.** Store `ExpW2` transposed at load (`weights.go:311` — one transpose per expert, once) and replace the loop with `matmulBTInto(x1, expW2T, contrib, 1, intermediate, D)` plus a scaled add. Take `scores`/`x1`/`out` from `*scratch` (add three fields to `ensureLayer`).

### 11. `wordPiece` allocates two strings per greedy-match probe

**Severity: Medium (performance)** — `embed/tokenize.go:516`

```go
		for end > start {
			sub := string(chars[start:end])          // alloc 1
			if start > 0 {
				sub = t.continuingPrefix + sub        // alloc 2
			}
			if id, ok := t.vocab[sub]; ok { ... }
			end--
		}
```

Plus `chars := []rune(word)` at `:505` and a separate `utf8.RuneCountInString` pass at `:502`.

**Failure scenario.** A 20-rune identifier probes ~20 candidates before matching, each costing two heap allocations — ~40 allocations per word, on the tokenizer that feeds both `embed.StaticModel.Encode` and every `encoder` entry point. Indexing 378k chunks × a few hundred words each is on the order of 10⁹ short-lived string allocations. This is precisely the cost `bm25` measured and pooled away (`bm25/tokenize.go:249`: "68.1% of indexing allocation count").

**Fix.** Build the candidate into a reused `[]byte` scratch with `"##"` pre-written, and look up via `t.vocab[string(buf)]` — the compiler elides that conversion for map lookups, so the probe loop becomes allocation-free. Hold the scratch in a `sync.Pool` (as `bm25` does) to keep `Encode` concurrent-safe.

### 12. `vision` never threads a `linalg.Workspace`, so every W8A8 projection heap-allocates its activation buffer

**Severity: Medium (performance)** — `vision/encoder.go:266`

Every matmul goes through `WeightMat.MatmulBT`, whose int8 path is:

```go
// linalg/quant.go:159
func MatmulBTW8A8(a []float32, bQ []int8, bScales []float32, dst []float32, M, K, N int) {
	var ws Workspace
	MatmulBTW8A8Into(&ws, a, bQ, bScales, dst, M, K, N)
}
```

A zero-value `Workspace` has no buffers, so `ws.int8Buf(M*K)` and `ws.f32Buf(M)` allocate on **every call**. `WeightMat.MatmulBTInto(ws, …)` exists for exactly this (`weightmat.go:131`), and `encoder` uses the pattern; `vision` and `ann` are the only consumers that don't. Separately, `vision/encoder.go:266-271` runs three `MatmulBT` calls on the same `x` (q/k/v) and `qwen_encoder.go:457-461` two (gate/up) — the exact case `linalg.MatmulBTW8A8Batch` (`quant.go:234`) was written to fuse into one quantize + one fork/join.

**Failure scenario.** SigLIP-so400m with `quant=true`: per layer the int8 activation scratch is 4·(4096·1152) + 4096·4304 ≈ 41 MB; over 27 layers ≈1.1 GB per image, plus 3× redundant activation quantization on q/k/v and 3× the goroutine fork/join.

**Fix.** Create one `linalg.Workspace` per `Forward` call (as `Workspace`'s doc requires) and switch to `MatmulBTInto`; route q/k/v and gate/up through `MatmulBTW8A8Batch`.

### 13. `scorePaged` re-quantizes the query and allocates a fresh `Workspace` for every block

**Severity: Medium (performance)** — `ann/flat_i8_mmap.go:119`

```go
	for b, r0 := 0, 0; r0 < f.n; b, r0 = b+1, r0+f.blockRows {
		r1 := min(r0+f.blockRows, f.n)
		f.pager.Touch(b)
		linalg.MatmulBTW8A8(q, f.bq[r0*f.dim:r1*f.dim], f.scales[r0:r1], dst[r0:r1], 1, f.dim, r1-r0)
	}
```

Each call allocates via `var ws Workspace` (see #12) and re-runs `quantizeRowInt8` over the identical query row. `pagerMu` is already held for the whole loop, so a persistent workspace is trivially safe.

**Failure scenario.** A 10 M-vector, `dim=1024` paged index has `blockRows = 1 MiB/1024 = 1024` ⇒ ~9,766 blocks per query: ~9,766 heap allocations plus ~9,766 redundant O(dim) quantizations (≈10 M wasted round-and-clamp ops) per single query — on the path whose entire purpose is making larger-than-RAM queries viable.

**Fix.** Keep a `linalg.Workspace` on `FlatI8` (guarded by the already-held `pagerMu`) and call `linalg.MatmulBTW8A8Into(&f.ws, …)`. Output stays byte-identical, per the argument already in the comment at `:108-112`.

### 14. `MatmulBTQ8` / `MatmulBTQ4` have no Workspace variant and allocate a K-wide scratch per call

**Severity: Medium (performance)** — `linalg/quant.go:88`, `linalg/quant.go:473`

```go
	parallelCols(M*N*K, N, func(j0, j1 int) {
		deq := make([]float32, K) // per-worker scratch: one widened b-row
```

`weightmat.go:141-142` acknowledges the gap and falls straight through:

```go
	case w.q8 != nil:
		MatmulBTQ8(a, w.q8, w.scales, dst, M, w.cols, w.rows)   // ignores ws
```

**Failure scenario.** The W8A8/W4A8 kernels were re-engineered around `Workspace` because "a decode loop calls ~168 matmuls per token; without reuse each allocates its quantized activation … which dominated alloc_space" (`workspace.go:3-7`). The weight-only Q8 path — the one the encoder's own accuracy notes prefer, since W8A8 "fell below the 0.97 reranker bar" (`forward_q8.go:23`) — still pays that cost: at K=3072, 168 calls × 12 KB ≈ 2 MB of garbage per token, plus one allocation per worker on the parallel path.

**Fix.** Add `MatmulBTQ8Into(ws, …)` / `MatmulBTQ4Into(ws, …)` taking `deq` from `ws.f32Buf(K)` on the serial path (and a per-worker slice of `ws.f32Buf(workers*K)` on the parallel one), then wire them into `WeightMat.MatmulBTInto`.

### 15. `detectCodeFence` accepts 4 leading spaces where the code's own rule (and CommonMark) is 0–3

**Severity: Medium** — `chunk/markdown/scanner.go:204`

```go
	// CommonMark allows 0-3 spaces of indent before a fence.
	i := 0
	for i < len(body) && i < 4 && body[i] == ' ' {
		i++
	}
```

The guard runs the body at `i = 0,1,2,3`, consuming **four** spaces. So `"    ```"` is treated as a fence toggle (5+ spaces correctly are not).

**Failure scenario.** A document demonstrating fence syntax inside a 4-space-indented code block, with an odd number of such lines:

````
To start a code block, type:

    ```

then your code.

## Next Section
````

Line 2 flips `inFence` and nothing closes it. Every later line becomes `lineCodeInside`, `## Next Section` is never `lineHeadingATX`, `boundaries == [0]`, `splittable` all-false — the rest of the document collapses into one oversized chunk with no heading sections (and hits finding #7).

**Fix.** `for i < len(body) && i < 3 && body[i] == ' '`.

### 16. `sparse.Scores` accumulates float64 over randomized map iteration — non-reproducible scores and tie flips

**Severity: Medium** — `sparse/sparse.go:105`

```go
	for t, w := range qw {
		if w == 0 { continue }
		for _, p := range ix.postings[t] {
			scores[p.doc] += w * float64(p.w)
		}
	}
```

`qw` is a Go map, so iteration order is randomized per execution and each document's score is summed in a different order; float64 addition is not associative.

**Failure scenario.** A query whose three terms contribute 0.1, 0.2, 0.3 to document A: `0.1+0.2+0.3 == 0.6000000000000001` but `0.2+0.3+0.1 == 0.6`. If document B scores exactly 0.6, `Query`'s tie test at `:150` (`items[a].Score != items[b].Score`) sometimes sees a tie and applies the ascending-doc-id rule and sometimes doesn't — so A vs B flips between calls in the same process, against the explicit promise at `:117` ("ties broken by ascending document id for determinism"). The sibling `bm25.Scores` (`bm25/query.go:47`) walks the query **slice** in order with a `seen` set and is deterministic; the two retrievers are inconsistent.

**Fix.** Dedup while walking `q.Terms` in index order — keep the map only as a `seen` set and accumulate into an ordered `[]struct{t uint32; w float64}` — then walk postings in that fixed order.

### 17. `chunk.Register` writes an unsynchronized package map that `Get` reads on every `ChunkFile`

**Severity: Medium** — `chunk/registry.go:60`

```go
var registry = map[string]Chunker{}
...
func Register(name string, c Chunker) { registry[name] = c }
```

`Register` is documented as part of the "PUBLIC, 1.0-committed chunker surface" (`registry.go:23`) and explicitly invited for runtime use ("External `mcp.Run` authors call this directly"). `Get` (`:64`) reads the same map and runs on every `ChunkFile` (`:94`), as does `Get("line")` from `markdown.lineFallback` (`markdown.go:92`) and `treesitter.fallback` (`chunker.go:359`).

**Failure scenario.** An author registers a chunker from a config-reload handler, a per-request path, or a `TestMain` running beside a parallel indexing test → `fatal error: concurrent map read and map write`, which is unrecoverable. `chunk/chunk.go:11` cites "the `database/sql` way", but `database/sql.Register` takes `driversMu.Lock()` precisely to prevent this. `treesitter.KenToTreeSitter` (`chunk/treesitter/languages.go:28`) is the same shape — an exported mutable map read by `poolFor` (`chunker.go:193`) on every file.

**Fix.** Guard `registry` with a `sync.RWMutex` (write-lock `Register`; read-lock `Get`/`Names`/`supports`) and unexport `KenToTreeSitter` behind an accessor. While there: `supports` calls `c.SupportedLanguages()` per file, and `chunk/regex/chunker.go:71-76` allocates *and* `sort.Strings`-sorts on each call — compute both packages' slices once in `init()`.

### 18. `StaticModel.encodeIDs` builds a slice-of-slices plus a weight slice on every Encode

**Severity: Medium (performance)** — `embed/model.go:181`

```go
	rows := make([][]float32, len(ids))
	w := make([]float64, len(ids))
	for i, id := range ids { ... rows[i] = m.embeddings[start : start+m.dim]; w[i] = ... }
	pooled := weightedMeanPoolSafe(rows, w, m.dim)
```

`weightedMeanPoolSafe` then allocates a third buffer (`sum := make([]float64, dim)`, `:242`) and pointer-chases through `rows`.

**Failure scenario.** This is the primary dense-retrieval path (README: "Primary dense retrieval uses Model2Vec static embeddings"). Embedding a 378k-chunk corpus at ~300 tokens/chunk costs ~1.1 M slice allocations for `rows`/`w` alone, plus a `[]float64` per call — and the gather loses sequential access because pooling reads through a slice-of-slices instead of indexing `m.embeddings` directly.

**Fix.** Fuse the two loops — accumulate into one `sum []float64` in the id loop, dropping `rows` and `w` entirely. The float64 precision contract at `:223-233` is preserved verbatim (same widen-then-multiply per element). Optionally expose `EncodeInto(dst []float32, text string)` so a batch caller can reuse `sum` too.

### 19. `Model.EncodeBatch` and `ModelQ8.EncodeBatch` are verbatim duplicates; `Close` is missing from `ModelQ8` and from the `Encoder` interface

**Severity: Medium (architecture)** — `encoder/model.go:265`

`model.go:133-196` and `model.go:265-320` are the same 60 lines — argument validation, concurrency defaulting, chunk-size arithmetic, the worker goroutine, per-item `EncodeQuery`/`EncodeDoc` dispatch, `errOnce`, the scatter back into `out` — differing only in which `forwardBatch` they call. `Encode` (`:96` vs `:246`) and `SetMaxSeqLength` (`:63` vs `:234`) are likewise duplicated. Relatedly, `Model` has `Close()` (`:78`) but `ModelQ8` has none, and the `Encoder` interface (`:18-22`) declares neither — so code holding an `Encoder` cannot release a mapping at all. (`ModelQ8` happens not to leak, because `LoadWeightsQ8` closes the handle internally at `weights_q8.go:107-109` — the asymmetry is in the API, not a live leak.)

**Fix.** Extract the shared body, e.g. `func encodeBatch(tok *embed.Tokenizer, maxSeq int, fwd func([][]int32) [][]float32, texts []string, isQueries []bool, concurrency int) ([][]float32, error)`, and have both methods pass their `forwardBatch`. Add `Close() error` to the `Encoder` interface with a no-op `ModelQ8.Close`.

### 21. Three divergent L2-normalize implementations, one of them dead

**Severity: Medium (architecture)** — `encoder/layernorm.go:44`

- `encoder/layernorm.go:44 l2Normalize(x, L, D)` — skips a row when `sumSq == 0`. **No non-test caller** (only `components_test.go:162,170`).

### 22. `regex` chunker's attach-block walk stops one line short of line 0

**Severity: Low** — `chunk/regex/chunker.go:144`

```go
		b := i
		for b-1 >= 1 && attachMatch(r, rawLine(b-1)) {
			b--
		}
		isBoundary[b] = true
```

`b-1 >= 1` can never let `b` reach 0; it halts at `b == 1`. When the attach block (doc comment, license header, decorators) starts at line 0 and runs into the first definition, `isBoundary[1]` — a line *inside* the comment — is set instead of `isBoundary[0]`, which the `for i := 1` filter at `:151` would have harmlessly dropped.

**Failure scenario.** A Python file opening with a >1500-byte `#` license header immediately followed by `def alpha():` (or a Rust `//!` module-doc block; both match `attach` per `python.go:34`, `rust.go:37`). `boundaries` contains `1`, so `emit(0, 1)` produces a **single-line first chunk** holding only line 0. `regex_test.go:78` can't catch it: it skips chunk 0, and chunk 1 legitimately starts on an attach line.

**Fix.** `for b > 0 && attachMatch(r, rawLine(b-1))`.

### 23. `vision.Preprocess` validates `cfg.Size` but not `cfg.Std` — silent `Inf`/`NaN` pixels

**Severity: Low** — `vision/preprocess.go:118`

```go
	if cfg.Size <= 0 {                                            // :58
		return nil, fmt.Errorf("vision: invalid target size %d", cfg.Size)
	}
...
	out[c*plane+dy*size+dx] = (v - cfg.Mean[c]) / cfg.Std[c]      // :118
```

`Config` is an exported struct with exported fields and no mandatory constructor (`Gemma3()` is a convenience). A zero `Std[c]` yields `+Inf` where `v != Mean[c]` and `NaN` where it equals.

### 24. HNSW build re-sorts an already-sorted candidate list and uses `sort.Slice` on the hot path

**Severity: Low (performance)** — `ann/hnsw.go:401`, `ann/hnsw.go:535`

`searchLayer` ends with `sort.Slice(out, …)` (`:401`) using `(sim desc, id asc)`. `selectNeighbors` then feeds that result to `selectHeuristic`, which immediately calls `sortCandsDesc` (`:499`) — `sort.Slice` with the *same* comparator plus a full copy (`:535-545`). The comment at `:463-466` acknowledges only `prune` passes an unsorted slice.

**Failure scenario.** During a build, `searchLayer` runs once per layer per insert with `ef = efConstruction = 200`, and `selectNeighbors` follows each call. That is two reflection-based `sort.Slice` passes over 200 elements plus one 200-element copy per (insert, layer), where one `slices.SortFunc` would do — `sort.Slice`'s `reflectlite.Swapper` closure is measurably slower than the generic sort on small slices.

**Fix.** Switch both to `slices.SortFunc`, and have `selectHeuristic` take an `alreadySorted bool` (or split into `selectHeuristicSorted`) so the `searchLayer` caller skips the redundant sort+copy; only `prune` pays it.

## What's solid

- **`ann` HNSW persistence is genuinely hardened.** `hnsw_persist.go` bounds every allocation-driving length against remaining bytes (`readLen`, `:185`), guards the `ndocs*dim` *product* in int64 on both the int8 and f32 branches (`:261`, `:274`), recomputes `mL` rather than trusting a possibly-`Inf`/`NaN` serialized value (`:246-252`), rejects trailing bytes, and validates full graph integrity (entry range, `maxLayer` vs entry-node layer, every neighbor id and its layer) before returning. The classic "hostile header drives a huge `make`" hole is closed.
- **The safetensors parser's alignment and lifetime handling is careful and correct.** `reinterpretLE` (`safetensors.go:518`) checks `uintptr(p)%Alignof` and falls back to an aligned copy rather than risking a checkptr throw or SIGBUS; the shape×dtype cross-validation at `:387-411` bounds the running product before multiplying; `mergeShards` repoints `t.owner` to the aggregate so `KeepAlive` guards the right object (`:184-188`); the shard-index path rejects `..`, absolute, and separator-bearing names (`:166`). Every byte-reading accessor carries `defer runtime.KeepAlive(t.owner)`.
- **The `mmap` package itself is clean.** `MapReadOnly` closes the fd on every path including both error returns; `PageAlignedInterior` rounds start up and end down so adjacent members' spans provably cannot overlap (which is what makes `SpanCache` eviction safe); `SpanCache`'s accounting is internally consistent and the `c.lru.Len() > 1` guard correctly avoids evicting the member just faulted in. Its only appearance above is a *caller* bypassing the mutex its documented contract requires.
- **The numerical-parity discipline in `encoder`/`embed` is real, not decorative.** LayerNorm, softmax, mean pooling and L2 all accumulate in float64 with the reasoning recorded inline; `MatmulBT`'s M-invariance contract is stated, tested, and preserved through the packing path (`packKBlockFor`, `matmul_blocked.go:194`, keeps k-tiling bit-identical for transformer dims); `parallelSpawnCols` rounds shards to a multiple of 8 so fan-out width is numerically inert.
- **`fuse`, `chunk/lines`, `bm25.Tokenize`, and `chunk/treesitter`'s line arithmetic are correct.** `RRFWeighted`/`RSFWeighted` (the `firstSeen` unique-per-key fallback makes the map-iteration build order irrelevant), `LineChunker`'s overlap clamping and trailing-newline handling, `Tokenize`'s pooled-buffer aliasing claims (`lowerString`'s slow path returns a fresh copy, so nothing aliases the reset scratch), and `linesBefore`/`trailingNewlineCorrection` were all traced — no defects.
